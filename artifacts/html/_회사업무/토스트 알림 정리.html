색 구분 기준

토스트 타입은 작업의 종류(수정·삭제)가 아니라 결과를 나타냅니다. 삭제가 성공하면 초록입니다 — 삭제라서 빨간 게 아닙니다.

타입언제예시
success 초록요청한 작업이 완료됨 등록·수정·삭제·복사·다운로드 완료
warn 노랑사용자가 뭔가 채우거나 고쳐야 함 제목을 입력해 주세요 · 권한이 없습니다
error 빨강시스템이 실패함 저장하지 못했습니다 · 불러오지 못했습니다

호출 방법 — 두 번째 인자를 꼭 넘기세요

const { toast, show, dismiss } = useToast();

{/* 화면 상단 고정이므로 페이지에 한 번만 렌더한다 */}
<ToastBanner toast={toast} onDismiss={dismiss} />

show('평가가 저장되었습니다.', 'success');
show('저장에 실패했습니다.', 'error');
show('입력값을 확인해 주세요.', 'warn');

useToast의 기본 타입은 'error'입니다. 타입을 빼먹으면 성공 메시지도 빨갛게 뜹니다. 이것이 ③번 원인이었습니다.

판정 기준이 어긋나 있었습니다

분기를 넣었는데도 계속 두 개가 떴습니다. 두 곳이 403을 다르게 판단하고 있었기 때문입니다.

판정 조건
전역 알림 http.ts HTTP 403 또는 OPS-4030 또는 COS-4030
페이지 apiTypes.ts OPS-4030 만

자료공유가 그 차이를 드러냈습니다 — 응답 상태는 403인데 업무 코드는 OPS-4040(NotFound)였습니다. isForbiddenError를 전역 알림과 같은 조건으로 맞췄습니다. httpStatus는 원래 오류 객체에 붙어 있던 값이라 새로 만든 것이 없습니다.

부수 효과

  • 토스트 2개 이상이면 8px 간격으로 세로 정렬
  • 컨테이너는 pointerEvents: none — 토스트가 없을 때 뒤쪽 클릭을 막지 않음

화면은 원래 정상이었습니다

useCommonCodeOptions는 조회 실패 시 기본 카테고리로 대체합니다. 이 대체 동작은 원래 있던 것이고 손대지 않았습니다. 사용자가 조치할 수 없는 영문 알림만 없앴습니다.

백엔드 영향 없음

suppressForbiddenEvent는 fetch에 들어가지 않는 브라우저 안에서만 쓰는 플래그입니다.

  • 요청 URL·헤더·메서드 동일
  • 서버 403 응답 동일
  • 오류 throw와 호출부 .catch 그대로
  • 브라우저 토스트만 생략

건드리지 않은 것

권한 신청 2화면의 전용 토스트

/permissions/requests/new · /permissions/requests/{id}/review 는 공통 useToast가 아니라 각 파일이 만든 로컬 함수와 .permission-toast 전용 CSS를 씁니다.

  • 타입 인자가 없어 항상 초록 — 실패해도 성공처럼 보입니다
  • 지속시간 2800·3000ms, 닫기 버튼 없음
  • 호출부 5곳과 렌더 마크업을 함께 바꿔야 해 이번 범위에서 제외

전용 CSS를 가진 다른 알림

window.alert를 쓰는 11개 파일(루브릭 편집, 학생 응시 등)도 그대로입니다. 브라우저 기본 대화상자라 성격이 다르고, 흐름을 막는 것이 의도일 수 있습니다.

조회 위주 catch 3곳

분류게시판 · 서비스 요청 검토 · 평가설계 상태. 조회 API는 403이 날 일이 거의 없어 후순위로 뒀습니다.
